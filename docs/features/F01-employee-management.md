> **Short form:** Creation and maintenance of employee master data (Sales
> Persons), their employment contracts (Employee Work Details), their
> recurring availability blocks (Unavailable), and their assignment to
> shift plans.

## 1. What is it? (Business context)

Employee Management is the foundation of the entire Shifty data model:
nearly every other domain (Bookings, Absences, Extra Hours, Reporting,
Billing Periods) hangs off a `sales_person.id`. This cluster holds four
tightly interlocked aggregates:

1. **Sales Person** — the employee's master data (name, identifying
   color, `is_paid`, `inactive`, optional link to a user login).
2. **Employee Work Details** (the historically grown name for the
   **employment contract**) — weekly hours, working days, vacation
   entitlement, dynamic/cap flags, and a fixed "committed voluntary" per
   week, valid for a time range `[from_year/kw/dow, to_year/kw/dow]`.
3. **Sales Person Unavailable** — one entry per (Sales Person, year,
   calendar week, day of week) on which the employee does **not** want
   to be scheduled (recurring availability block at day-of-week
   granularity — not the Absence system for whole Vacation/sick
   periods, which lives in F02).
4. **Sales Person Shiftplan** — which shift plans the employee is allowed
   to be booked into, with permission level (`available` or
   `planner_only`).

From the user's perspective (see `docs/employee-management_de.md` and
`docs/employee-management.md` for the end-user manual with screenshots),
the onboarding flow is:

1. **Create the entry** via *User Management → Create entry*
   (`shifty-dioxus/src/page/person_detail.rs`). Since v2.7 Phase 63 one
   dialog creates a sales person, a login account, or both on the *same*
   person identity; afterwards the admin lands on the person detail page and
   enters the identifying color, `is_paid`/`inactive` and the shift-plan
   assignments there. The dialog itself is deliberately lean [D-63-07] — see
   §4.7. The page is gated on `admin`, not on HR (§4.6, D-62-08).
2. **Set up an employment contract** via the employee detail page
   (`shifty-dioxus/src/page/employee_details.rs`) in the *Contracts*
   area → `ContractModal`. Without a contract the employee has no
   target hours and the balance remains empty.
3. **Optionally enter Unavailable weekdays** — the sales user does this
   themselves via the weekly view in the shift planner.
4. **Optionally enter Extra Hours** manually (Cluster F02 — Extra Hours /
   Absences, not here).

Deactivation ("This person is inactive") is the preferred alternative
to actual deletion; deletion is exposed as a soft-delete by the backend
service, but is deliberately not offered in the UI in order to preserve
the balance history and FK consistency with Bookings/Extra Hours.

## 2. Business rules

### 2.1 Sales Person

- **Visibility of `is_paid` is privacy-sensitive.** Non-HR users see
  `is_paid = None` (`SalesPersonServiceImpl::get_all`,
  `service_impl/src/sales_person.rs:62-70`). In `get()` the field is
  only returned if the calling user is HR **or** the caller is the
  linked user of the Sales Person record itself
  (`sales_person.rs:120-143`).
- **Delete = soft delete.** `delete()` sets `deleted` to the current
  timestamp and rotates `version` (`sales_person.rs:253-279`). The
  `deleted` field is **not modifiable via update()**
  (`ValidationFailureItem::ModificationNotAllowed("deleted")`, `sales_person.rs:228-235`).
- **Optimistic locking via `version`.** Update requires that the
  submitted `version` matches the persisted value; otherwise
  `ServiceError::EntityConflicts` (`sales_person.rs:220-226`).
- **Create guards.** `id != Uuid::nil()` → `IdSetOnCreate`; `version !=
  Uuid::nil()` → `VersionSetOnCreate` (`sales_person.rs:177-183`). Both
  `id` and `version` are generated by the service via `UuidService`.
- **User assignment is 1:1.** Both `UNIQUE` indexes on `person_id`
  (`sales_person_person_id_unique_idx`, `user_person_id_unique_idx`,
  `migrations/sqlite/20260916000000_create-person-backfill.sql`) enforce it in
  the database. Replacement runs in a TX via `discard_assigned_user` +
  `assign_to_user` (`sales_person.rs:316-342`), so an assignment move is
  atomic.
- **Linking is a merge of two persons** (v2.7, Phase 61 [D-61-03]).
  `SalesPersonDaoImpl::assign_to_user` moves the user onto the sales person's
  `person_id` and deletes the absorbed `person` row. The sales person keeps its
  identity — it is the side carrying historic weight (bookings, `extra_hours`,
  write-once snapshots in `billing_period_sales_person`).
- **Only genuine ambiguity is rejected** (v2.7, Phase 61 [D-61-04]). Before any
  write, `assign_to_user` runs two conflict `SELECT`s: does another user
  already hang off the sales person's person, and does another sales person
  already hang off the user's person? Either hit returns
  `DaoError::EntityAlreadyExists` **without writing anything**;
  `SalesPersonServiceImpl::set_user` translates that into
  `ServiceError::EntityAlreadyExists` → HTTP 409. The common post-backfill case
  — both sides already carry their *own* person — is explicitly **not** a
  conflict and goes through.
- **Unlinking is a split** (v2.7, Phase 61 [D-61-05]).
  `discard_assigned_user` keeps the sales person on its person and gives the
  user a **freshly created** one. Order is mandatory: insert the new `person`
  row first, move the user second — the other way round would leave the user
  transiently without a valid `person_id` and therefore without self-access.
  No carrier-less `person` row is ever left behind.
- **A re-link A→B runs as split(A) + merge(B)** (v2.7, Phase 61 [P-61-B]).
  `set_user` unconditionally calls `discard_assigned_user` before
  `assign_to_user`, so user A is left with its own fresh person and stays a
  plain user. Both steps share one service transaction: if the merge fails with
  409, the split rolls back with it and the original state survives untouched.
- **All four reading link paths resolve via `person_id`** (v2.7, Phase 61
  [D-61-08]). `SalesPersonDaoImpl::find_by_user`,
  `find_sales_person_by_user_id`, `get_assigned_user` and
  `get_all_user_assignments` join
  `sales_person sp JOIN user u ON u.person_id = sp.person_id` instead of going
  through the link table. The authorisation decision lives **entirely in SQL**
  on purpose: an equivalent Rust comparison of two `Option<Uuid>` would
  evaluate `None == None` as `true` and go fail-open, while SQL's three-valued
  logic never lets `NULL = NULL` be true. This is a **permanent convention**,
  not a phase note — see
  [`../architecture/04-auth.md` §Self-access gate for sales-person data](../architecture/04-auth.md#self-access-gate-for-sales-person-data).
  Covered by `service_impl::test::person_self_gate` (11 tests against a real
  in-memory SQLite database). The before/after permission matrix it used to run
  [D-61-09] was a *temporary* artefact: it needed both data models in one
  fixture database, and since
  `migrations/sqlite/20260917000000_drop-sales-person-user.sql` the "before"
  half cannot be produced any more. It was removed in Phase 61; the
  accept/reject assertions against the `person_id` implementation stay as
  permanent regression guards.
- **None of the four paths filters `deleted IS NULL` — and none may start to.**
  `verify_user_is_sales_person` hangs off `get_assigned_user`, so a soft-delete
  filter added later would silently take self-access away from a soft-deleted
  Sales Person. Locked by
  `person_self_gate::soft_geloeschte_sales_person_behaelt_selbstzugriff`.

### 2.2 Employee Work Details (employment contract)

- **Time range in calendar-week granularity** via
  `(from_year, from_calendar_week, from_day_of_week)` up to
  `(to_year, to_calendar_week, to_day_of_week)`. The "active" contract
  for a week is determined by a tuple comparison:
  `(from_year, from_calendar_week) <= (year, calendar_week) <= (to_year, to_calendar_week)`
  (`service_impl/src/employee_work_details.rs:114-118`). **[To verify]**
  whether `from_day_of_week` / `to_day_of_week` are deliberately
  ignored in this comparison — the current implementation only relies
  on calendar-week granularity.
- **Weekly hours distribution.** `expected_hours` is the weekly total;
  `workdays_per_week` is the divisor for `hours_per_day()`; the checked
  weekday flags (`monday`..`sunday`) define which days are candidates at
  all (`potential_weekday_list`,
  `service/src/employee_work_details.rs:78-102`).
- **Holiday hours.** `holiday_hours = expected_hours / potential_days_per_week`
  — that is, a holiday falling on a potential working day relieves the
  employee by this share (`employee_work_details.rs:112-114`).
- **`is_dynamic` (v1.5)** — instead of fixed weekly hours, the actually
  worked hours count as the agreed hours (target = actual). Migration
  `20251029192107_add-column-is-dynamic-to-employee-work-details.sql`.
- **`cap_planned_hours_to_expected` (v2.x)** — caps the balance-relevant
  hours per week to `expected_hours`; anything above that counts as
  volunteer work (see `docs/employee-management_de.md` §6). Migration
  `20260426120000_add-cap-flag-to-employee-work-details.sql`.
- **`committed_voluntary` (v2.4)** — weekly firmly committed voluntary
  hours in addition to the paid target; takes effect in the annual
  overview and capacity planning. Migration
  `20260623120000_add-committed-voluntary-to-employee-work-details.sql`.
- **Vacation proration at contract edges (D-28-04, Phase 28).**
  `vacation_days_for_year(year)` prorates at year start and year end:
  start → `vac * (ordinal(from) - 1) / days_in_year(year)` (strictly
  before the start; a Jan 1 start subtracts 0),
  end → `vac * (1 - ordinal(to) / days_in_year(year))`
  (`employee_work_details.rs:158-194`). Regression suite starting at
  `employee_work_details.rs:286-408`.
- **Update is partial and does NOT change `from_*`.** `update()` only
  writes `to_*`, `expected_hours`, `vacation_days`, `workdays_per_week`,
  `is_dynamic`, `cap_planned_hours_to_expected`, `committed_voluntary`
  and `version`
  (`service_impl/src/employee_work_details.rs:240-253`). Weekday flags
  and the start point remain as they were on create — changing these
  fields requires a new contract.
- **Create guards.** `id != nil` → `IdSetOnCreate`; `version != nil` →
  `VersionSetOnCreate` (`employee_work_details.rs:197-208`). `created`
  is set by the service.
- **Delete = soft delete.** `delete()` sets `deleted` and keeps the
  record for history (`employee_work_details.rs:262-288`).

### 2.3 Sales Person Unavailable

- **One record per weekday per CW.** `create()` checks whether an
  undeleted row already exists for
  `(sales_person_id, year, calendar_week, day_of_week)` and otherwise
  rejects with `ServiceError::EntityAlreadyExists`
  (`service_impl/src/sales_person_unavailable.rs:155-168`).
- **Create guards.** `id`, `version`, `deleted` and `created` must be
  empty, otherwise `IdSetOnCreate` / `VersionSetOnCreate` /
  `DeletedSetOnCreate` / `CreatedSetOnCreate`
  (`sales_person_unavailable.rs:143-154`).
- **Delete = soft delete.** Sets `deleted` and rotates `version`
  (`sales_person_unavailable.rs:190-230`).
- **Auth gate.** All read/write ops accept **either** a Shiftplanner
  **or** the sales user themselves (via
  `SalesPersonService::verify_user_is_sales_person`,
  `sales_person_unavailable.rs:41-50`, `73-82`, `132-141`, `203-212`). The
  week-wide bulk query `get_by_week()` is **only** available to
  Shiftplanners (`sales_person_unavailable.rs:109-111`).

### 2.4 Sales Person Shiftplan

- **Permission level per assignment.** `permission_level` ∈
  {`available`, `planner_only`} — CHECK constraint in the migration
  `20260402000000_add-permission-level-to-sales-person-shiftplan.sql:1`.
- **"Leave empty = allowed everywhere".** If a Sales Person has **no**
  shift plan assignment at all, they count as bookable in **every**
  shift plan instance (`get_bookable_sales_persons` / `is_eligible`,
  `service_impl/src/sales_person_shiftplan.rs:100-118` and `137-140`).
- **`planner_only` blocks self-booking.** The person appears in
  `get_bookable_sales_persons` only if the calling user is a
  Shiftplanner (`sales_person_shiftplan.rs:114-115` and
  `147-154`).
- **Inactive Sales Persons are never listed.** Filter in
  `get_bookable_sales_persons` (`sales_person_shiftplan.rs:96-99`).
- **Full replace on set.** `set_shiftplans_for_sales_person`
  writes the assignment list completely fresh, in the same TX, after
  verifying the existence of the Sales Person
  (`sales_person_shiftplan.rs:52-75`).

### `PersonDao` — access to the identity parent (v2.7, Phase 61)

`dao::person::PersonDao` / `dao_impl_sqlite::person::PersonDaoImpl` is the
only read/write path onto the `person` table. Phase 61 pinned it to exactly
four methods; Phase 63 added the four the facet lifecycle needs and nothing
beyond them:

| Method | Purpose |
| --- | --- |
| `find_by_id(id, tx)` | Single identity lookup, `Option<PersonEntity>`. |
| `create(entity, process, tx)` | Insert. `id`, `created` and `version` are generated by the service, not by the DAO; no SQLite rowid is read back — `person.id` is a `blob(16) PRIMARY KEY`, not a rowid alias. |
| `sales_persons_without_user(tx)` | Sales persons whose person carries no login user — candidates for "add login". Filters `sp.deleted IS NULL`. |
| `users_without_sales_person(tx)` | Login users whose person carries no *live* sales person — candidates for "add person". The sales-person side is restricted to non-deleted rows **inside the `ON` clause** (`AND sp.deleted IS NULL`), so a user whose only sales person was soft-deleted becomes a candidate again instead of dropping out of both candidate lists [D-62-05 / WR-02]. The `user` table itself still has no soft-delete column. |
| `delete(id, tx)` | Removes the `person` row (v2.7, Phase 63). Hard delete — `person` carries no `deleted` column. The DAO deletes the ID it is given and judges nothing; the decision whether the row *may* go belongs to `PersonDetailService::remove_facet` (§4.7). |
| `has_live_facets(person_id, tx)` | Does the person still carry at least one **live** carrier? (v2.7, Phase 63.) The trigger condition of the orphan cleanup — see the reading of "live" below. |
| `find_by_sales_person(sales_person_id, tx)` | Resolves a sales person back to its person. **Resolves, does not judge:** a soft-deleted sales person still yields its person; whether that carrier counts is the business of `has_live_facets`. |
| `find_by_user(username, tx)` | The counterpart for a login name — the way to learn the *winning* identity after a merge [D-61-03]. |

`PersonEntity` carries `id`, `created`, `version` and nothing else — the same
reduced shape as the table itself [D-60-04].

**Both candidate reads are LEFT JOIN anti-joins over `person_id`, not
emptiness checks on that column [D-61-02].** After the Phase 60 backfill every
`sales_person` and every `user` row carries a person, so "unlinked" means
*there is no join partner on the other side*, not *the value is missing*. The
regression guard is
`service_impl::test::person_candidates::kandidat_trotz_gesetzter_person_id`:
every fixture row has a non-NULL `person_id`, and both candidate sets are
still non-empty.

**A soft-delete filter on the optional side of an outer join belongs in the
`ON` clause, never in the `WHERE` clause [D-62-05 / WR-02].** Put into `WHERE`,
the LEFT JOIN degenerates into an INNER JOIN and the anti-join loses exactly
the rows it exists to find. That is what the Phase 61 review recorded as
finding WR-02 on `users_without_sales_person`: a user whose only sales person
had been soft-deleted still had a *formal* join partner and therefore dropped
out of **both** candidate lists — the sales person was no "add login"
candidate because of the delete filter, and the user was no "add person"
candidate because of the join partner. He could never be linked again. The
watchdog for the fix is
`service_impl::test::person_candidates::user_mit_nur_soft_geloeschter_sales_person_ist_kandidat`:
it seeds exactly that constellation and asserts the user is a candidate. The
same rule carries the directory join below; both occurrences in
`dao_impl_sqlite` are marked with a line comment naming D-62-05 / WR-02, so
moving the filter back into `WHERE` reads as a contradiction on the spot.

### `PersonDirectoryDao` — the person directory read path (v2.7, Phase 62)

`dao/src/person_directory.rs` + `dao_impl_sqlite/src/person_directory.rs`.
A deliberately separate trait, **not** a fifth method on `PersonDao`: that
trait is pinned to exactly four methods, and the directory is a different
reading of the same tables — `PersonDao` serves identity and candidate
anti-joins, this DAO serves the aggregate across all three shapes.

| Method | Purpose |
| --- | --- |
| `list_directory_entries(tx)` | All directory rows in exactly one statement — a three-way outer join `person` ↔ `sales_person` ↔ `user` [D-62-02]. Unsorted; ordering belongs to the business-logic service so it stays testable and locale-independent. |
| `all_user_roles(tx)` | All role assignments of all users as a **single** bulk query. `PermissionDao::roles_for_user` stays untouched — it has its place in the auth path, but one call per directory row would be exactly the N+1 pattern this phase removes. |
| `find_directory_entry(person_id, tx)` | The single directory row of one person (v2.7, Phase 63) — the same three-way join as `list_directory_entries`, with the same two join rules, narrowed by `person.id = ?`. `None` for an unknown *and* for a carrier-less person: the detail view follows the directory's visibility rule exactly, so it never answers a half-empty row. |

`PersonDirectoryRow` is flat. The sales-person side (`sales_person_id`,
`sales_person_name`, `background_color`, `is_paid`, `inactive`) is empty
exactly when the person carries no *live* sales person; `username` is empty
exactly when the person carries no login account. At least one side is always
filled.

**Two join rules carry the whole semantics:**

- `AND sp.deleted IS NULL` sits in the **`ON` clause**, never in `WHERE`. In
  `WHERE` the LEFT JOIN degenerates into an INNER JOIN and every person
  without a sales person would drop out of the directory — the same trap as
  WR-02 in the candidate read path. Guard:
  `service_impl::test::person_directory_dao::soft_geloeschte_sales_person_laesst_benutzer_sichtbar`.
- `WHERE sp.id IS NOT NULL OR u.name IS NOT NULL` excludes carrier-less
  `person` rows — a person with neither a live sales person nor a login
  account has nothing to show. Guard:
  `service_impl::test::person_directory_dao::person_ohne_traeger_erscheint_nicht`.

Soft-deleted sales persons do not appear, inactive ones do [D-62-04]:
"inactive" is a display state with its own badge, "deleted" is absence.

**Lifecycle of the `person` row — what "carrier-less" means [D-63-01,
reading (b), fixed in Phase 63].** A person is *alive* as long as at least one
carrier is alive: a `user` row with that `person_id` (any — `user` has no
delete column) **or** a `sales_person` row with that `person_id` and
`deleted IS NULL`. **A soft-deleted sales person counts as gone.** It is
invisible in the directory join anyway (D-62-04), so it no longer keeps an
admin view alive. When `remove_facet` takes the last live carrier, the
`person` row is deleted in the *same* transaction.

**The accepted price, named explicitly:** the soft-deleted `sales_person` row
keeps a `person_id` that no longer resolves to anything. That is not a defect
but the documented consequence of this reading — there is deliberately no
foreign key from `sales_person.person_id` onto `person(id)` (the Phase 60
migration adds the column plus a unique index, no FK). A later cleanup pass
must **not** "repair" this dangling pointer:
`billing_period_sales_person` references `sales_person.id` and never
`person.id`, so write-once snapshots stay untouched. Guard:
`service_impl::test::person_detail_dao` (D-4).

### Relationships

All tables of the cluster hang off `sales_person(id)` via foreign key
(exception: `sales_person_shiftplan` additionally hangs off
`shiftplan(id)`). SQLite only checks FKs if `PRAGMA foreign_keys=ON` is
active, **and it is** — sqlx enables it on every connection by default
(`sqlx-sqlite-0.8.6/src/options/mod.rs:185`), even though the project code
itself never sets the pragma. A grep of `*.rs`/`*.sql` therefore finds
nothing and is misleading here; `PRAGMA foreign_keys` reads `1` at runtime,
and a dangling insert is rejected with `FOREIGN KEY constraint failed`.

What the check does not cover is the soft-delete semantics
(`WHERE deleted IS NULL`): a soft-deleted parent is still a row, so the FK
stays satisfied while live queries see a reference that resolves to nothing
(see `docs/domain/edge-cases.md` §8). That limit is why FK enforcement buys
less here than it looks.

The identity parent `person` (v2.7, Phase 60) sits above both carriers.
Both edges are optional and unique: a person may have a user **or** a sales
person **or** both, and nothing auto-creates the missing counterpart
[D-60-03]. Details in
[`../architecture/03-data-model.md`](../architecture/03-data-model.md).

```
person ─┬─ 0..1 ─ user          (user.person_id — nullable, UNIQUE)
        └─ 0..1 ─ sales_person  (sales_person.person_id — nullable, UNIQUE)

                                        sales_person ──┬──< employee_work_details
                                                       ├──< sales_person_unavailable
                                                       └──< sales_person_shiftplan >── shiftplan

(user ↔ sales_person runs exclusively through the shared person since
 v2.7 Phase 61 — there is no link table any more.)
```

### 4.6 `PersonDirectoryService` (v2.7, Phase 62)

Trait: `service/src/person_directory.rs`.
Implementation: `service_impl/src/person_directory.rs`.

```rust
async fn list(&self, ctx, tx) -> Result<Arc<[PersonEntry]>, ServiceError>;
```

The aggregate behind the single person list that replaces the former tabs of
the user administration. `PersonEntry` carries `person_id`, `kind`,
`display_name`, `username`, `sales_person_id`, `background_color`, `is_paid`,
`inactive` and `roles`.

**Fat backend [PADM-06, D-62-03].** Display name and shape are computed
exactly once — here, in the service. The display name is the sales person
name where present, otherwise the username; it is never `Option` and never
empty. This derivation is deliberately *not* a SQL `COALESCE` and *not* a
frontend fallback: a second source of the same truth is how the two drift
apart. `PersonKind` (`Linked` / `SalesPersonOnly` / `UserOnly`) is an explicit
backend fact [D-62-01], never derived client-side from empty `Option`s.

Sorting is case-insensitive by display name and also lives in the service, not
in the SQL: SQLite compares `TEXT` case-sensitively by default, so ordering in
the query would make `Zacharias` sort before `mia`.

**Auth gates** (`service_impl/src/person_directory.rs`):

| Method | Allowed roles |
| --- | --- |
| `list` | admin |

`check_permission("admin", …)` is the **first statement** of the method,
before any database access [D-62-08, PADM-08, threats T-62-01 / T-62-05].
This is the deliberate tightening the module header of `PersonService` (§4.5)
announced: the directory is the administrator's person management, and it
discloses usernames and role assignments. The privilege is the string literal
`"admin"` — the same one `PermissionServiceImpl::get_all_users` requires; an
`ADMIN_PRIVILEGE` constant deliberately does not exist in the repo.

On a missing privilege the error is **propagated**. There is no redaction to
empty fields as in `VoluntaryStatsService` — a redacted response would be
indistinguishable from an empty directory. Guard:
`service_impl::test::person_directory::list_ohne_admin_privileg_ist_forbidden`.
The permission mock in that test file only accepts the literal `"admin"`, so
an HR-gated implementation fails every test in the file.

**Deliberate behaviour change — HR without admin loses the sales person
administration [PADM-08, D-62-08].** Today `create` / `update` / `delete` on
the Sales Person aggregate are gated on `HR_PRIVILEGE`
(`service_impl/src/sales_person.rs`), while the user administration already
demands `"admin"` (`service_impl/src/permission.rs`). The merged page cannot
carry two gates, so it carries the stricter one: an HR user without the admin
role loses access to the sales person administration. This was decided
explicitly by the user on **2026-09-16**, after the consequence had been
named — see `.planning/REQUIREMENTS.md` §"Bewusste Änderung gegenüber heute".
Handing HR a section-wise part of the person administration back is tracked as
PADM-F-02 (future), not as a defect. Both sides of the gate are proven over
HTTP, not only at service level:
`shifty_bin::integration_test::person_directory::admin_bekommt_200` and
`shifty_bin::integration_test::person_directory::hr_ohne_admin_bekommt_403`.
The negative test additionally asserts that the response body carries none of
the seeded names, so a `200` with an empty or redacted list would not pass
silently.

**Tier.** Business-Logic. The `gen_service_impl!` block binds exactly three
dependencies — `PersonDirectoryDao`, `PermissionService`, `TransactionDao` —
and deliberately no other domain service. It is still Business-Logic and not
Basic: it merges the two carrier aggregates of a person into one view and owns
the `PersonKind` invariant across them. `shifty_bin/src/main.rs` constructs it
in the business-logic block, i.e. after the basic services and therefore
strictly after `person_service` — no `OnceLock`, no forward declaration. See
`docs/architecture/02-service-tiers.md` for the tier rule this case sharpens.

**REST.** `GET /person-directory` answers `200` with `[PersonEntryTO]`, `403`
for non-admins and `500` otherwise; handler
`rest::person_directory::get_person_directory`. The handler carries **no**
second permission check — the trust boundary is `PersonDirectoryService::list`,
and two gate sites would be two truths of which the weaker one is the hole
(T-62-13). OpenAPI registration is `PersonDirectoryApiDoc`, merged into
`ApiDoc` in `rest/src/lib.rs` (`CLAUDE.md` §REST API). The prefix is a
four-place contract: router nest, `ApiDoc` nest, frontend URL
(`shifty-dioxus/src/api.rs`) and the `[[web.proxy]]` entry in
`shifty-dioxus/Dioxus.toml`. **The dev-proxy entry belongs to the path**, not
to a later cleanup — a missing one has already cost this repo three shipped
dev-server 404s (T-62-14). Details in §5.4.

**Scope boundary.** Phase 62 delivered the list, nothing else. During
Phase 62 a row still linked to the two facet-specific detail pages of the
time [D-62-07]. Phase 63 replaced both of them with the single person detail
page and the mutations per facet (adding a missing facet, the candidate
picker, facet-aware delete confirmation) — see §4.7
[PADM-02/03/04/05/07]. The two old routes and their pages were removed
without replacement; there is deliberately no redirect.

**Edge cases.**

- A directory row without any carrier is `unreachable!()` — the SQL already
  excludes that case (62-01), so a panic here is a data-integrity alarm about
  a violated `person`/`sales_person`/`user` invariant [D-61-01, D-61-05],
  accepted as threat T-62-10.
- Soft-deleted sales persons do not appear, inactive ones do, with
  `inactive == Some(true)` [D-62-04].
- Roles come from a single bulk query and are grouped by username in the
  service [D-62-06]. A person without a login account gets an empty role list,
  never `None`.

**Transport.** `impl From<&PersonEntry> for PersonEntryTO` and
`impl From<&PersonKind> for PersonKindTO` live in `rest-types/src/lib.rs`
behind `#[cfg(feature = "service-impl")]`. The mapping is purely field-wise;
it recomputes nothing, in particular not the display name.

### 4.7 `PersonDetailService` (v2.7, Phase 63)

Trait: `service/src/person_detail.rs`.
Implementation: `service_impl/src/person_detail.rs`.

```rust
async fn get_detail(&self, person_id, ctx, tx) -> Result<PersonEntry, ServiceError>;
async fn get_detail_by_sales_person(&self, sales_person_id, ctx, tx) -> Result<PersonEntry, ServiceError>;
async fn unlinked_sales_person_candidates(&self, ctx, tx) -> Result<Arc<[SalesPerson]>, ServiceError>;
async fn unlinked_user_candidates(&self, ctx, tx) -> Result<Arc<[Arc<str>]>, ServiceError>;
async fn create_combined(&self, request: &CreatePersonEntry, ctx, tx) -> Result<Uuid, ServiceError>;
async fn add_facet(&self, person_id, facet: PersonFacet, display_name, username, ctx, tx) -> Result<Uuid, ServiceError>;
async fn remove_facet(&self, person_id, facet: PersonFacet, ctx, tx) -> Result<(), ServiceError>;
```

`PersonFacet` (`User` / `SalesPerson`) is the *target of an action*, not the
state of a row — that is `PersonKind` from §4.6. `CreatePersonEntry` carries
`display_name`, `wants_user`, `wants_sales_person` and an optional `username`.

**The detail aggregate: core row plus targeted reloads.** `get_detail`
returns exactly the directory row of §4.6 — `kind`, `display_name`,
`username`, `sales_person_id` and the sales-person fields, all derived in the
backend. The four sections of the page (master data, shift-plan assignment,
roles, invitations) load through their own, already running endpoints instead
of being folded into one fat response. That keeps the "no N+1" requirement:
a bounded call *per section for exactly one person* is not an N+1 — an N+1
would be a call per **list row**. The alternative (one aggregate carrying all
four sections) would have duplicated four transport shapes without saving a
single request.

An unknown `person_id` and a carrier-less person are **both**
`EntityNotFound` → 404, never a half-empty answer: a person without a login
and without a live sales person is invisible in the directory [D-62-04], and
the detail view follows that visibility rule exactly.

**Creation path — one entry, selectable facets [PADM-02, SC-2].**
`create_combined` creates the login account, the sales person, or both, and
both hang off the **same** person. The two writes run in **one** transaction:
if either fails, neither exists afterwards and no orphan `person` row remains.
The rule "at least one facet must be selected" is enforced **server-side**,
before a transaction is even opened — the disabled submit button in the
frontend is UX, not the boundary [D-63-07, ASVS V5]. An empty selection, a
missing/blank `username` on `wants_user` and a blank `display_name` on
`wants_sales_person` are all `ValidationError` → **422**.

**Adding a facet — and why the answer carries an id [PADM-03, SC-3,
D-61-03].** `add_facet` creates exactly the missing object and leaves the
existing one untouched (same `id`, same `version`, same name). The two
directions are **not** symmetric, and that asymmetry is the detail a later
reader would otherwise take for a bug:

- **Adding the user side** hangs the new login onto the *existing* person
  (`PermissionDao::create_user(.., Some(person_id), ..)`). The `person_id`
  stays the same.
- **Adding the sales-person side** cannot do that. A freshly created sales
  person brings its **own** identity along [D-61-01], and merging the two
  lets the **sales person win** [D-61-03]: the user moves over to it and the
  absorbed person disappears. The entry therefore **changes its
  `person_id`**.

`add_facet` returns the **resulting** id, not the one that was passed in.
Callers must use the return value; anyone reusing the input points at
nothing. The linking itself runs through the unchanged Phase 61 write path
(`SalesPersonDao::assign_to_user`) — no second linking path was built, so
merge direction, conflict detection and absorption stay in one place. An
already occupied side is `EntityAlreadyExists` → **409**, the same contract
as `POST /sales-person/{id}/user` [D-61-04]. A missing mandatory name is
**422**.

**Delete semantics per facet — deliberately asymmetric [PADM-07, SC-5,
D-63-05].**

| Facet | Semantics | What goes with it |
| --- | --- | --- |
| `User` | **Hard delete** of the `user` row | Roles and open invitations, through the schema's FK cascade — deliberately no additional application-level deletes that could drift from the schema |
| `SalesPerson` | **Soft delete** through the `deleted` stamp | Nothing. The row stays so that shift-plan history and the write-once `billing_period_sales_person` snapshots remain untouched |

**There is no "remove both" button.** `remove_facet` always takes exactly one
`PersonFacet`; a combined action is ruled out by D-63-05, because no single
confirmation text could honestly describe two delete semantics at once. A
missing side is `EntityNotFound` → 404.

Afterwards the carrier check runs (`PersonDao::has_live_facets`) and, if the
person lost its last live carrier, the `person` row is deleted **in the same
transaction** [D-63-01]. The reading of "carrier-less" and its accepted
consequence are documented in §3 under `PersonDao`.

**Candidate reads [PADM-04, SC-4].** `unlinked_sales_person_candidates` and
`unlinked_user_candidates` are the two lists behind the picker ("add login" /
"add person"). Already linked targets do **not** appear there. That is
convenience, **not** the security boundary: `POST /sales-person/{id}/user`
rejects an occupied target with 409 regardless [D-61-04]. Whoever bypasses
the list, or loses the race between loading and submitting, runs into the
rejection instead of a silent overwrite. The hiding *complements* the
server-side rejection; it does not replace it.

**Auth gates** (`service_impl/src/person_detail.rs`):

| Method | Allowed roles |
| --- | --- |
| `get_detail` | admin |
| `get_detail_by_sales_person` | admin |
| `unlinked_sales_person_candidates` | admin |
| `unlinked_user_candidates` | admin |
| `create_combined` | admin |
| `add_facet` | admin |
| `remove_facet` | admin |

`check_permission("admin", …)` is the **first statement** of every method —
before validation and before any database access [D-62-08, PADM-08, threats
T-63-04-A/B, T-63-05-A].

**This is stricter than the basic services underneath, on purpose.**
`SalesPersonService` is gated on `HR_PRIVILEGE` and `PersonService` on HR as
well; the merged person administration cannot carry two gates, so it carries
the stricter one — exactly the tightening the module header of §4.5
announced. An `ADMIN_PRIVILEGE` constant deliberately does not exist in the
repo; the gate is the string literal `"admin"`. Consequence: the service
calls the HR-gated basic services with `Authentication::Full` internally —
reachable only *after* its own, stricter gate has passed, and never derived
from a request. Passing the user context through instead would reject an
admin without the HR role for no reason.

**Tier.** Business-Logic. The `gen_service_impl!` block binds **eight**
dependencies: `PersonDirectoryDao`, `PersonDao`, `PermissionDao`,
`SalesPersonDao`, `PersonService`, `SalesPersonService`, `PermissionService`,
`TransactionDao`. Two of them are basic services — which the tier convention
explicitly allows; forbidden is only the other direction. Neither
`PersonService` nor `SalesPersonService` knows this aggregate, and no other
service consumes it (it hangs off the REST handlers only), so there is no
cycle. Construction in `shifty_bin/src/main.rs` happens strictly **after** the
basic block, in the business-logic section directly following
`person_directory_service` — no `OnceLock`, no forward declaration. See
[`../architecture/02-service-tiers.md`](../architecture/02-service-tiers.md).

**Why the user side goes through `PermissionDao` and not
`PermissionService`.** `service::PermissionService` deliberately carries
**no** `Transaction` associated type — roughly twenty services hold it as a
dependency, so an associated type there would be a workspace-wide ripple
without benefit. The transaction-capable write paths
(`create_user` / `delete_user`) therefore sit one layer lower, on
`dao::PermissionDao`. Details in
[`../architecture/05-transactions.md`](../architecture/05-transactions.md)
and [F12 §4.6](./F12-auth-session.md).

**Known edge (pre-existing, deliberately not fixed in Phase 63).**
`session.user_id` is the only foreign-key relation pointing at `user(name)`
**without** a cascade (migration `20241116224840_add-session.sql`). Deleting
a user who still holds an open session runs into a foreign-key error and
surfaces at the endpoint as a generic **500** instead of a speaking
rejection. A fix would be a schema change outside this phase's locked
decisions and belongs in its own change.

## 7. Edge cases

For the central reference see
[`../domain/edge-cases.md`](../domain/edge-cases.md). Feature-specific
edges for this cluster:

- **Changing `from` on a running contract is not supported.** `update()`
  only writes back the `to_*` fields + core parameters; anyone wanting
  to shift a start point has to end the existing contract and create a
  new one. See §2.2. Cf. also §1.2 in edge-cases (contract switch).
- **Contract gap between two contracts.** `find_for_week` returns
  `EntityNotFoundGeneric` if the week lies between two contracts
  (`service_impl/src/employee_work_details.rs:119-126`). Reporting
  consumers must handle this case — see edge-cases §1.2.
- **Contract-end proration for non-Dec 31 endings.**
  `vacation_days_for_year` subtracts
  `vac * (1 - ordinal(to) / days_in_year)` at year-end; a Dec 31 ending
  subtracts 0. Regression guards from
  `service/src/employee_work_details.rs:286-408`.
- **Sales Person `is_paid` masking.** Anyone who is not HR and **not**
  themselves the linked user gets `is_paid = None` — not `false`.
  Wrong interpretation in the frontend as "unpaid" would be a
  downstream info leak. See §2.1 and `sales_person.rs:120-143`.
- **Delete = soft delete.** All delete endpoints only set `deleted`.
  Subsequent `create()` calls can create **the same name** again
  (no `UNIQUE(name)`), but the FK subgraph (Bookings, Extra
  Hours, Absences) still hangs off the original record. See
  edge-cases §8.
- **User assignment race.** Since v2.7 Phase 61 the 1:1 guarantee is carried
  by `user_person_id_unique_idx`. A replacement runs `discard_assigned_user`
  (split) + `assign_to_user` (merge) in the same TX [P-61-B]. Two parallel HR
  requests assigning the same login user to two different Sales Persons no
  longer produce a generic DAO error: `assign_to_user` detects real ambiguity
  **before** any write and returns `DaoError::EntityAlreadyExists`, which
  `set_user` translates into `ServiceError::EntityAlreadyExists` → **HTTP 409**
  [D-61-04]. The unique index remains the second line of defence for the race
  loser.
- **`sales_person.background_color`.** Free hex field — no format
  check in the backend. Invalid values (`"red"`, empty string) land raw
  in the DB and render in the frontend as style `background-color:` —
  the style attribute silently ignores garbage. **[To verify]** whether
  validation is worthwhile.
- **Weekday blocks across the year boundary.** `sales_person_unavailable`
  stores `(year, calendar_week)`. Per ISO 8601, CW 1 can lie in
  December of the previous year — consumers must consistently handle
  the semantics of `(iso_week_year, iso_week)`. See edge-cases §4.
- **Shift plan assignment: "empty = everywhere".** This is by design
  (onboarding convenience), but it causes a freshly created Sales
  Person to appear as bookable in **every** shift plan until they get
  a first assignment. Anyone wanting more restrictive behavior must
  deliberately set a non-assignment on creation.
- **`planner_only` semantics.** Sales users **cannot** book themselves
  into such plans — the person doesn't appear in
  `get_bookable_sales_persons` for non-Shiftplanners in the first
  place. The booking service (F03) MUST check `is_eligible` so that
  direct API calls don't open a hole.
- **`get_all` also returns soft-deleted persons.** The DAO method
  `all` in `dao_impl_sqlite/src/sales_person.rs` **[To verify]**
  filters on `deleted IS NULL`; in the frontend the user management
  list also shows inactive but not deleted persons. Anyone needing
  a Sales Person list of "really all ever created" has to build a
  special read — no such endpoint exists at the moment.
- **A soft-deleted Sales Person keeps its person identity forever.** The
  unique index on `sales_person.person_id` is full, not partial — deletion
  does **not** release the identity [D-60-01]. Consequence: an employee who
  leaves and comes back appears as a *second* person, because the new Sales
  Person row gets a new identity. That is deliberate — releasing the identity
  would let two different humans occupy the same one over time and would make
  write-once `billing_period_sales_person` snapshots resolve to the wrong
  person. Merging two persons is not v2.7 scope.
- **A Sales Person without a login is a permanently supported shape.**
  Volunteers without a user account are as valid as HR/admin users without a
  Sales Person (see [F12](./F12-auth-session.md)). `person_id` stays nullable
  on purpose, and **nowhere** is a user created automatically alongside a
  Sales Person [D-60-03].
- **Adding a sales person changes the `person_id` of the entry** (v2.7,
  Phase 63 [D-61-03]). Adding the *user* side keeps the identity; adding the
  *sales-person* side merges, and the sales person wins. `add_facet` and
  `POST /person/{id}/facet` therefore answer with the **resulting** id, and
  every caller has to use it. The frontend reloads through the returned
  `person_id`, never through the one it sent. After the Phase 61 path
  `POST /sales-person/{id}/user` it does not even know the new id — that is
  what `GET /person/by-sales-person/{id}` exists for. Anyone reusing the
  input id points at a row that no longer exists.
- **Removing a facet is hard on one side and soft on the other** (v2.7,
  Phase 63 [D-63-05]). "Delete login" removes the `user` row for good, taking
  roles and open invitations with it through the FK cascade; "delete sales
  person" only sets the `deleted` stamp, so history and billing snapshots
  survive. The two confirmation dialogs say so in different words on purpose,
  and there is no button that does both at once.
- **The last facet takes the person with it** (v2.7, Phase 63 [D-63-01]). See
  §3 — a soft-deleted sales person counts as gone, so its `person_id` can end
  up dangling. Accepted, documented, and not to be "fixed" by a later cleanup
  pass.
- **Deleting a user with an open session surfaces as a 500** (pre-existing,
  named in Phase 63, deliberately not fixed). `session.user_id` is the only
  FK onto `user(name)` without a cascade. See §4.7.
- **Assignment on creation** (v2.7, Phase 61 [D-61-01]): since then,
  `SalesPersonDaoImpl::create` **first** inserts its own `person` row and
  writes that ID into `sales_person.person_id`. Both statements run on the
  transaction handed in by the caller — identity assignment is therefore
  atomic with the Sales Person insert, and a rollback takes both rows with
  it. The 16-byte ID is generated in Rust (`Uuid::new_v4()`); reading back the
  SQLite row number would be wrong because `person.id` is a `blob(16) PRIMARY
  KEY`, not a rowid alias. `created` is produced by
  `strftime('%Y-%m-%dT%H:%M:%S.000000000Z','now')` — the same format as the
  Phase-60 backfill so that `Iso8601::DATE_TIME` parses it, which keeps the
  DAO layer free of a `ClockService` dependency. The trait signature of
  `SalesPersonDao::create` is unchanged. Evidence:
  `service_impl::test::person_creation` (N-1 through N-4).
