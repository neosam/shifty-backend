<objective>
Das Planungs-Soll im Backend einfuehren: ein additives Feld `planning_target_hours` an
`ShortEmployeeReport` und `ShortEmployeeReportTO`, an BEIDEN Konstruktionsstellen
(`assemble_weeks` und `get_reports_for_all_employees`) tatsaechlich berechnet, und durch
eine Testmatrix abgesichert, die die beiden Stellen gegeneinander haelt.

**Die eine nicht-triviale Entscheidung dieses Plans** (aus `64-RESEARCH.md` § Kern-Mechanismus
uebernommen und gegen den Code nachgeschaerft, hier als Vorgabe festgeschrieben): Die Feiertags-
und Abwesenheits-Reduktionsterme, die heute schon im Code stehen, sind an ein Gate gekoppelt, das
fuer dynamische Vertraege IMMER wahr ist. Sie duerfen deshalb fuer das Planungs-Soll nicht
wiederverwendet werden. Das Planungs-Soll bekommt eine eigene, parallele Reduktionsrechnung mit
einem Gate aus ZWEI Bedingungen: es gibt eine Vertragszeile fuer diese Woche
(`has_contract_row`), UND der Rohwert ist groesser 0 — wobei der Rohwert am ungezwungenen
Element 1 des `weight_for_week`-Tupels gemessen wird, nicht am fuer dynamische Vertraege auf 0
gezwungenen Element 0.

**Warum beide Bedingungen, und warum die zweite nicht der alte Fehler ist.** `weight_for_week`
gibt Element 0 als `if is_dynamic { 0.0 } else { expected_hours * relation }` zurueck und
Element 1 als `expected_hours * relation` ohne Bedingung. Der Bilanzpfad gated auf Element 0 —
darum ueberspringt er die Reduktion fuer JEDE Woche eines dynamischen Vertrags. Das neue Gate
gated auf Element 1. Fuer einen dynamischen Vertrag ist Element 1 die volle Vertragsgroesse, also
greift die Reduktion (Erfolgskriterium 3). Fuer einen nicht-dynamischen Vertrag sind Element 0 und
Element 1 identisch, also schalten altes und neues Gate unter genau derselben Bedingung — die
Zeichengleichheit ist damit STRUKTURELL und gilt fuer alle nicht-dynamischen Zeilen, auch fuer
eine mit 0 Vertragsstunden oder fuer eine Randwoche, in der die Vertragszeile keinen einzigen
potenziellen Werktag beitraegt (`relation == 0.0`). Ein Gate, das nur `has_contract_row` prueft,
wuerde in genau diesen Faellen von einer 0-Basis abziehen und ein negatives Planungs-Soll
erzeugen, waehrend das bilanzrelevante Soll bei 0 bleibt (Erfolgskriterium 4 nur zufaellig
erfuellt, naemlich solange keine solche Zeile existiert).

**Nicht zusaetzlich auf 0 klemmen.** Kein `.max(0.0)` auf dem Ergebnis. Der bestehende
Bilanzpfad klemmt auch nicht, und ein Klemmen wuerde die Zeichengleichheit genau in den Faellen
mit schwerer Abwesenheit brechen, in denen das bestehende Feld ebenfalls negativ wird. Ein
negatives Planungs-Soll bleibt unter derselben pathologischen Eingabe moeglich wie heute beim
bilanzrelevanten Soll — diese Konsistenz ist es, was Erfolgskriterium 4 verlangt.

**Zweite, davon unabhaengige Asymmetrie:** Der dynamische Zweig in
`get_reports_for_all_employees` berechnet die Feiertags-/Abwesenheits-Groessen heute gar nicht
— sie existieren nur im Normal-Zweig. Ein Task, der Stelle A nur nach Stelle B spiegelt, kompiliert
nicht. Die Bausteine muessen vor die Dreiwege-Verzweigung gehoben werden.

**Gepinnte Randbedingungen, die in diesem Plan nicht neu verhandelt werden:**

- `weight_for_week` behaelt seine Signatur. Element 1 des Rueckgabetupels traegt den benoetigten
  Rohwert bereits heute, und beide Aufrufer destrukturieren ihn schon.
- Kein Snapshot-Schema-Bump. `service_impl/src/billing_period_report.rs` liest ausschliesslich
  `service::reporting::EmployeeReport` — ein anderer Typ, erzeugt von einem dritten, hier nicht
  beruehrten Codepfad. Der Snapshot-Schreiber kann das neue Feld nicht sehen. Niemand bumpt
  `CURRENT_SNAPSHOT_SCHEMA_VERSION` "sicherheitshalber".
- Keine neue REST-Route und kein neuer Dev-Proxy-Eintrag. `GET /report` und
  `GET /report/week/{year}/{calendar_week}` existieren und liefern das erweiterte DTO automatisch mit.
- `get_year` bekommt das Feld gratis, weil es derselbe `assemble_weeks`-Helfer ist (D-64-02).

Purpose: Die Zahl, die das Frontend in Plan 64-02 anzeigen soll, muss vorher existieren und
nachweislich richtig sein.
Output: ein Modell-Feld, ein DTO-Feld, zwei berechnende Konstruktionsstellen, fuenf Tests.
