# Phase 63 — UI Design Contract

> Visual and interaction contract for `/person/:person_id/` (one component, three
> Ausprägungen) and its mutation surfaces — Anlege-Dialog, Facet-Add-Aktionen,
> Kandidaten-Picker, Verknüpfung-lösen und die beiden ausprägungs-spezifischen
> Lösch-Bestätigungen. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.

**Stack reality:** Dioxus (Rust → WASM), not React. No shadcn, no npm
component library, no CSS-in-JS. Design tokens are CSS custom properties in
`shifty-dioxus/input.css` (light + dark) bound to Tailwind class names via
`shifty-dioxus/tailwind.config.js`. This is the **same token set Phase 62
used** — nothing here is invented, and every value is either copied from that
system or lifted from the two pages this phase retires
(`page/user_details.rs`, `page/sales_person_details.rs`), **retokenized**
where those pages used the pre-redesign legacy palette (see "Legacy-Class
Retokenization" below — this is a mandatory, not optional, part of the port).

### Legacy-Class Retokenization (mandatory)

`page/user_details.rs` and `page/sales_person_details.rs` — the two pages
this phase retires (D-63-04) — predate the design-token migration and are
full of forbidden legacy classes: `text-gray-*`, `bg-white`, `bg-blue-*`,
`bg-green-*`, `bg-red-*`, `bg-yellow-*`, `border-gray-*`. The project's own
`no_legacy_classes_in_source` self-test (18 instances already in the
codebase, canonical shape at `page/employees.rs:18-43`) **forbids these in
any new/redesigned source file**, including a brand-new file that ports old
markup. The new `page/person_detail.rs` is a new file → the test applies. Do
not copy-paste the old class strings; every structural pattern below states
its **retokenized** replacement explicitly so the executor never has to
improvise a mapping. A `no_legacy_classes_in_source` self-test is required in
the new file (same template as Phase 62's `page/user_management.rs`).

| Legacy class (old pages) | Retokenized replacement |
|---|---|
| `text-gray-800` (headings) | `text-ink` |
| `text-gray-600` / `text-gray-500` (secondary text) | `text-ink-soft` / `text-ink-muted` |
| `bg-white` (card surface) | `bg-surface` |
| `bg-gray-50` / `bg-gray-100` (row/panel background) | `bg-surface-alt` |
| `border` / `border-gray-200` | `border-border` |
| `bg-blue-600 text-white` (buttons) | `Btn { variant: BtnVariant::Primary }` (or `Secondary`) — never a raw button element |
| `bg-blue-50 border-blue-200 text-blue-700` (info callout, `ShiftplanAssignmentsInfo`) | `bg-surface-alt border border-border text-ink-soft` — a **neutral** callout, not a 4th accent colour (see Color section — this page already uses accent + warn + bad, a 5th hue is unnecessary) |
| `bg-green-100 text-green-800` (Active/Valid pill) | `bg-good-soft text-good` |
| `bg-yellow-100 text-yellow-800` (Expired pill) | `bg-warn-soft text-warn` |
| `bg-blue-100 text-blue-800` (Redeemed pill) | `bg-accent-soft text-accent` |
| `bg-red-100 text-red-800` (SessionRevoked pill) | `bg-bad-soft text-bad` |
| `focus:ring-2 focus:ring-blue-500 focus:border-blue-500` (raw `input`) | Use `TextInput` (`component/form/inputs.rs`) — already carries the correct focus-ring token, never hand-roll a raw `input` with focus classes |
| `<button class="bg-blue-600 ...">Copy</button>` (invitation copy button) | `Btn { variant: BtnVariant::Secondary }` |
| `mr-3 p-2 text-gray-600 hover:text-gray-800 hover:bg-gray-100 rounded-md` (back button) | `text-ink-soft hover:text-ink hover:bg-surface-alt rounded-md` |

## Typography

Reuses five of the project's seven fixed sizes (adds `h2` to the four Phase
62 declared, since this page — unlike the flat list — has nested section
headers):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Page heading (`<h1>`, the entry's `display_name`) | 22px (`text-h1`) | 600 (semibold) | 28px (1.27) |
| Section heading (`<h2>` — Stammdaten, Schichtplan-Zuordnung, Rollen, Einladungen) | 18px (`text-h2`) | 600 (semibold) | 24px (1.33) |
| Body (form fields, dialog copy, confirmation text) | 14px (`text-body`) | 400 (regular) | 20px (1.43) |
| Label (`Field` labels, table header caps) | 11px (`text-micro`, via `Field`'s `LABEL_CLASSES`) | 600 | 14px (1.27) |

**Weight deviation, documented on purpose (same rationale as Phase 62):**
this page uses `font-medium` (500, pills), `font-semibold` (600, `h1`/`h2`
headings), and `font-bold` (700, uppercase table-header micro-labels
— none on this page, carried only for consistency with the rest of the
project's token system). Three-weight use is a pre-existing, codebase-wide
convention, not a new exception.

### Row actions on `/user_management/` — one recommended change, flagged explicitly

The existing list row (`page/user_management.rs`) currently renders a 🗑
delete button wired to a **generic** `DeleteUserConfirmDialog`
("Are you sure you want to delete user {username}? This cannot be undone.")
for any row with a user side. That generic copy cannot satisfy D-63-08's
ausprägungs-aware requirement (it doesn't mention roles/invitations being
hard-deleted, and it has no soft-delete counterpart for a sales-person row at
all). **Recommendation: remove the row-level 🗑 delete button and its
`DeleteUserConfirmDialog` entirely; both delete actions live exclusively on
the detail page from this phase forward.** Row actions become: Edit link +
"Act as this person" (impersonate) only, for entries with a user side. This
keeps exactly one place in the app where an admin can delete anything, and
that one place carries the correct, ausprägungs-aware copy. Flagged here
rather than silently decided because it touches `page/user_management.rs`,
which is nominally Phase 62's file — the planner should confirm this
explicitly rather than have it discovered as a diff surprise.

## Open Questions

For the orchestrator to relay as plain text — each item states the decision
taken above and the rejected alternative.

1. **Row-level delete button removed from `/user_management/` in favor of
   detail-page-only delete.** See "Row actions" above. Decision taken:
   remove it, because the generic confirmation copy cannot satisfy PADM-07's
   ausprägungs-aware requirement without either duplicating D-63-08's two
   text blocks into the row dialog (adds an inline dialog to a table that
   already delegates all mutation UI to dedicated pages/dialogs) or leaving
   a second, weaker delete path alongside the new one. **Rejected
   alternative:** keep the row button too, pointing it at the same new
   confirmation dialogs the detail page uses — technically possible, but
   then delete becomes reachable from two places with no clear "canonical"
   one, and the row has less room to show the last-facet addendum
   correctly (it would need to know the *other* side's state, information
   the row already carries per Phase 62's aggregate but that increases the
   row's rendering complexity for a rarely-used action).

2. **"Verknüpfung lösen" styled Secondary, not Danger.** Decision taken:
   D-63-05 itself calls this action "harmlos, umkehrbar" — both objects
   survive fully intact. Styling it red alongside two genuinely destructive
   red buttons would visually claim an equivalence that doesn't exist.
   **Rejected alternative:** Danger styling for visual consistency with "this
   changes something irreversible-feeling" — rejected because it misrepresents
   the actual risk profile the CONTEXT.md decision table explicitly draws.

3. **Missing-facet card uses a neutral dashed border, not a warn/accent
   color.** Decision taken: reuses the retired `UserOnly` badge's exact
   "gap, not alarm" neutral-dashed visual language (a missing facet on a
   *new-ish* entry is an expected, normal state — the whole point of PADM-03
   is that filling it in is a first-class, easy action, not a fix for
   something wrong). **Rejected alternative:** `warn`-colored card to draw
   the eye to the gap — rejected because it re-introduces exactly the
   accent/warn "evaluative color on a non-evaluative distinction" problem
   the Phase 62 UAT already flagged and fixed once on this same page family.

4. **Candidate picker is a plain `SelectInput`, not a search-as-you-type
   list.** Decision taken: `REQUIREMENTS.md`'s own "Out of Scope" table rules
   out name-matching sophistication for this org size ("bei einer Handvoll
   Leute unnötig"). **Rejected alternative:** a searchable/filterable list —
   would be over-engineering for the stated scale and adds a new form-atom
   pattern this project doesn't have yet.
