# Phase 62 — UI Design Contract

> Visual and interaction contract for `/user_management/` — one searchable list
> replaces the two-tab layout. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.

**Stack reality:** this is a **Dioxus (Rust → WASM)** frontend, not React. There
is no shadcn, no npm component library, no CSS-in-JS. The "design system" is an
existing, already-locked internal token set: Tailwind CSS driven entirely by CSS
custom properties in `shifty-dioxus/input.css` (light + dark theme blocks) and a
fixed `fontSize` scale in `shifty-dioxus/tailwind.config.js`. Every value below is
copied from that existing system or from the closest analog component already
shipped on this exact page — nothing here is invented from scratch.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (not a shadcn-compatible stack) |
| Preset | not applicable |
| Component library | none — hand-rolled Dioxus atoms in `shifty-dioxus/src/component/atoms/` (`Btn`, `PersonChip`, `WeekStatusBadge`, …) |
| Icon library | none — no icon font/SVG-sprite system in this project; existing precedent uses a single emoji glyph (🗑 delete, 🥸 impersonate) or a plain colored dot (`span` with inline `background-color`) for the sales-person color swatch. This phase adds no new icon. |
| Font | Inter (`sans`), JetBrains Mono (`mono`, used for usernames) — `tailwind.config.js` `fontFamily` |
| Styling mechanism | Tailwind utility classes in `rsx!`, values resolved through CSS custom properties (`var(--accent)`, etc.) defined in `shifty-dioxus/input.css` for light (`:root`) and dark theme blocks. **Never** write raw hex/rgb in a class string or inline style except the per-row sales-person `background_color` swatch, which is genuinely dynamic per-entity data. |

## Spacing Scale

Declared values (must be multiples of 4) — this is the existing Tailwind default
scale as already used throughout `page/user_management.rs` and sibling pages,
not a new invention:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`gap-1`, `px-1`) | Chip icon gaps |
| sm | 8px (`gap-2`, `px-2`) | Compact element spacing — search bar to CTA gap, badge padding |
| md | 16px (`px-4`, `mb-4`) | Default element spacing — page horizontal padding at mobile, toolbar-to-table gap |
| lg | 24px (`px-6`, `mb-6`) | Section padding — page horizontal padding at `md:` breakpoint, page-title-to-toolbar gap |
| xl | 32px (`px-8`) | Layout gaps — page horizontal padding at `lg:` breakpoint |
| 2xl | 48px | Major section breaks — not used on this page (single-section layout) |
| 3xl | 64px | Page-level spacing — not used on this page |

Exceptions (already-established, reused verbatim, not new for this phase):
- Table cell padding is `py-2 px-3` (8px/12px) — smaller than the `sm` token,
  matches every existing table row in this codebase (`thead`/`tbody` cells).
- Badge/pill padding is `py-0.5 px-2` (2px/8px, `WeekStatusBadge`) or
  `py-px pl-[7px] pr-[4px]` (`PersonChip`) — sub-4px vertical padding is the
  established pill shape across the whole app; do not "fix" it to a 4px
  multiple in this phase.
- Button padding is `px-3 py-1.5` (12px/6px, `Btn` `BASE_CLASSES`) — established
  atom, not renegotiable per-phase.

## Typography

The existing `fontSize` scale (`tailwind.config.js`) bakes weight and line-height
into each named size — this is a **locked, project-wide system** (see the
`redesign-typography-bump` note in the config comment), not a per-phase choice.
Phase 62 reuses four of the seven existing sizes; it does not introduce new
ones.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Heading (page title `<h1>`) | 22px (`text-h1`) | 600 (semibold) | 28px (1.27) |
| Body (table cells, search input, dialog copy) | 14px (`text-body`) | 400 (regular) | 20px (1.43) |
| Label (table header caps, `thead th`) | 11px (`text-micro`) | 700 (`font-bold`, uppercase, `tracking-wide` via letter-spacing baked into the token) | 14px (1.27) |
| Small (badges/pills — Ausprägung badge, Paid/Volunteer/Inactive pills, role chips) | 12px (`text-small`) | 500 (`font-medium`) | 16px (1.33) |
| Display | 32px (`text-display`) | 700 | 38px (1.19) | not used in this phase — no display-scale element on this page |

**Weight deviation from the generic "2 weights max" rule, documented on purpose:**
this project's already-shipped token system uses three weight utilities in
practice — `font-medium` (500, pills/badges/chips), `font-semibold` (600,
headings and the bold-highlight `PersonChip` state), `font-bold` (700, uppercase
table-header micro-labels). This is a pre-existing, codebase-wide convention
(`WeekStatusBadge`, `PersonChip`, every table on this page today) — Phase 62
follows it rather than inventing a stricter 2-weight rule that would visually
diverge from every other table in the app.

## Layout & Components (supplementary — not part of the template's fixed sections, kept for executor precision)

```
TopBar {}

  h1 "{i18n.t(Key::UserManagement)}"           // unchanged, text-h1 mb-6

  [ADMIN GUARD — see below; page returns early with "Not authorized." if not admin]

  Toolbar row (flex items-center gap-2 mb-4, existing SEARCH_INPUT_CLASSES reused):
    input[type=text]  — single search field (was two: sales_persons_search + users_search)
    Btn Secondary     — "Create new sales person" (was Primary — demoted, see Color/Copy)
    Btn Primary       — "Add new user" (unchanged style/position)

  table (single, replaces both SalesPersonTabContent + UsersTabContent tables)
    thead: Name | Type (Ausprägung) | Username | Sales person | Roles | (actions, no header)
    tbody: one row per PersonEntryTO, sorted case-insensitive by display_name

  [empty-state block, only when filtered list is empty and search term is non-empty]

AddUserDialog {}            // unchanged, D-62-06
DeleteUserConfirmDialog {}  // unchanged, D-62-06
```

**Removed entirely:** `UserManagementTabBar` / `UserMgmtTab` rendering call
(component itself may stay in the tree if another caller exists — Discretion

### Row anatomy (single row covers all three Ausprägungen — no conditional row *component*, only conditional *cells*)

| Cell | Always rendered? | Content |
|------|-------------------|---------|
| Name | always | color dot (`span w-2.5 h-2.5 rounded-full`, only if `background_color` present, i.e. entry has a sales-person side) + `display_name` text (`text-ink`) |
| Type (Ausprägung badge) | always | new `PersonKindBadge` atom — one of the three variants below |
| Username | always | `username` field, `font-mono text-ink` — per D-62-03 this is never empty (equals `display_name` for a `UserOnly` entry) |
| Sales person info | only if entry has a sales-person side | `PersonChip` Paid/Volunteer pill (unchanged from today) + `Inactive` badge (unchanged) — cell renders the `Unlinked` em-dash when absent |
| Roles | only if entry has a user side **and** roles are included in the aggregate (Claude's Discretion in RESEARCH.md — planner decides) | role chips (`bg-accent-soft text-accent`, unchanged) or the `Unlinked` em-dash |
| Actions | always, contents vary | `Edit` link → `Route::SalesPersonDetails` (has sales-person side) or `Route::UserDetails` (user-only, no sales-person side) per D-62-07; **plus**, only if entry has a user side: "Act as this person" `Btn Secondary` (impersonate) and 🗑 `Btn Danger` (delete) |

### `PersonKindBadge` atom (new — model directly on `WeekStatusBadge`)

Three variants, shape classes identical to `WeekStatusBadge`'s
(`inline-flex items-center px-2 py-0.5 rounded-sm text-small font-medium border`),
color classes per variant:

| Variant | Classes | Rationale |
|---------|---------|-----------|
| `Linked` | `bg-accent-soft border-accent text-accent` | "complete" pairing — reuses the accent "full/primary state" semantic already carried by the `Paid` pill on this page |
| `SalesPersonOnly` | `bg-warn-soft border-warn text-warn` | "missing a login" — reuses the existing `Volunteer`-pill amber semantic (incomplete/pending), not a new color |
| `UserOnly` | `border border-dashed border-border-strong text-ink-soft bg-transparent` | neutral — a pure login account (e.g. an admin-only account) is a normal end state, not a gap; reuses `PersonChip`'s existing no-color fallback style verbatim |

### Admin guard (component-level, D-62-08)

Copied **verbatim** from `page/settings.rs:556-570`, placed at the top of
`UserManagementPage` immediately after reading `AUTH`:

```rust
let is_admin = AUTH
    .read()
    .auth_info
    .as_ref()
    .map(|a| a.has_privilege("admin"))
    .unwrap_or(false);
if !is_admin {
    return rsx! {
        TopBar {}
        div { class: "p-md text-ink-muted", "Not authorized." }
    };
}
```

### Fat-Backend visual contract (PADM-06, grep-enforced)

`display_name` and `username` render as plain `"{...}"` interpolations. No
`.unwrap_or(...)`, `.or(...)`, or `if sales_person.name.is_some() { ... } else { ... }`
branching on the name fields anywhere in `page/user_management.rs`. The `kind`
badge is selected by a `match` on the backend-supplied `PersonKindTO`, never
derived from `Option`-emptiness of other fields.

## Open Questions

For the orchestrator to relay as plain text — each item states the decision
taken above and the rejected alternative.

1. **"Create new sales person" CTA demoted from Primary to Secondary.**
   Today it is `Btn variant=Primary` inside its own tab. Merging both tabs onto
   one toolbar row would put two Primary (accent) buttons side by side, which
   breaks the "accent reserved for one clear action" rule this spec declares.
   Decision taken: keep "Add new user" as the sole Primary CTA (logins are the
   more frequent admin action in this app's HR-admin context) and demote
   "Create new sales person" to Secondary. **Rejected alternative:** keep both
   Primary, matching the pre-merge visual precedent exactly — flag this to the
   user if the double-accent look is actually preferred.

2. **Ausprägung badge colors reuse `accent`/`warn`/neutral instead of a fourth
   distinct hue.** Decision taken: `Linked`=accent (echoes `Paid`),
   `SalesPersonOnly`=warn (echoes `Volunteer`), `UserOnly`=neutral dashed
   (echoes `PersonChip`'s no-color fallback) — all three reuse tokens already
   on this exact page rather than introducing new palette entries. **Rejected
   alternative:** a fourth genuinely new hue for one variant, or plain text
   labels with no color at all (since "Ausprägung" is categorical, not
   evaluative, a no-color argument is defensible — pick this if reusing
   `warn`/`accent` for a non-evaluative distinction feels misleading).

3. **New i18n key `ColumnUsername` instead of reusing `ColumnLinkedUser`.**
   `ColumnLinkedUser` ("Linked user") is semantically wrong once every row
   shows a username value (D-62-03 — even a `SalesPersonOnly` row's username
   cell renders the em-dash, but a `UserOnly`/`Linked` row always has a real
   value, not conditionally "linked"). Decision taken: propose a new key.
   **Rejected alternative:** reuse `ColumnLinkedUser` as-is and accept the
   slightly-off semantics to avoid a new key + i18n-parity-test edit.

4. **"Not authorized." stays a hardcoded, untranslated English string.**
   This inherits verbatim from the `page/settings.rs` guard this phase is
   instructed to copy "wörtlich" (D-62-08). It is a pre-existing i18n gap on
   every page that uses this guard pattern, not something introduced by Phase
   62. **Not fixing it here** keeps the guard copy-paste faithful to CONTEXT.md;
   flagging it in case the user wants a follow-up quick-task across all guarded
   pages instead of a silent one-off fix buried in this phase's diff.

5. **Roles column: kept in the merged list, exact data source left to the
   planner.** RESEARCH.md's Open Question 2 is unresolved on whether roles
   come from a new bulk-DAO query or a single extra request. This UI-SPEC
   assumes the column **stays visible** (D-62-06 lists it explicitly as
   migrating into the merged list) and specifies only its visual form (role
   chips, unchanged). If the planner decides the bulk-query cost outweighs the
   value for this phase, the fallback is to drop the column entirely (not to
   restore per-row N+1 loading) — that would be a scope deviation from
   D-62-06 and should be called out explicitly in the plan, not silently
   decided in code.
